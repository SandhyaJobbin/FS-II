<objective>
Introduce the rubric data model to the QUESTIONS bank and replace the ad-hoc `evaluateOpenTextBatch` grading path with a Gemini `responseSchema`-enforced `evaluateWithRubric` function living in `backend/AsyncGrading.gs`. Every rubric-requiring question (40 open_text + 10 hybrid — verified in RESEARCH.md A6) gets a rubric block; every LLM call gets structured output; every failure mode collapses to a locally-set `ungraded` verdict rather than the current silent `results[qId] = true` regression at Code.gs L177.

Purpose: This plan is the code-side foundation of Phase 10 Success Criteria 1 and 4 (GRADE-06 + GRADE-07). It deliberately does NOT touch the scoring loop, the GradingTranscripts sheet, or the recruiter override endpoint — those are separate plans (10-02, 10-03) so this plan can land and be sync-checked (10-04) without waiting on UI or admin work. The rubric criteria authoring workload (writing the 50 human-readable rubric blocks) is separated into plan 10-06 so that the *shape* of the change lands here even if content editing lags.

Output: `backend/Code.gs` with 50 QUESTIONS entries carrying a rubric skeleton block (per-criterion arrays with placeholders that plan 10-06 fills), plus a `handleStartAttempt` client-strip guarantee. `backend/AsyncGrading.gs` with the new `evaluateWithRubric` function.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Candidate browser -> handleStartAttempt response | Untrusted client receives the question payload; rubric MUST NOT cross this boundary or the grading criteria are leaked |
| AsyncGrading.gs -> Gemini v1beta generateContent | Outbound API call with the candidate's raw answer text; prompt-injection risk if answer is not delimited |
| Gemini response -> local parse | JSON parse of model output; must default to ungraded on failure, never silent-true |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01a | Information Disclosure | `handleStartAttempt` client projection | high | mitigate | Allowlist projection stays intact; Task 3 adds a load-bearing SECURITY comment forbidding future maintainers from adding `rubric` to the allowlist. Rubric criteria never appear in the client payload — same trust boundary as `model_answer` today. |
| T-10-01b | Tampering | Gemini prompt via candidate answer field (prompt injection) | high | mitigate | Task 2 frames the candidate answer with unique `<<<ANSWER_START>>>` / `<<<ANSWER_END>>>` delimiters and the system prompt explicitly instructs the model to treat delimited text as data, not instructions. The `responseSchema` enum enforcement is the defense-in-depth: even a compromised prompt cannot make the model return an out-of-enum verdict (RESEARCH.md Pitfall 4). |
| T-10-01c | Tampering | LLM output silent-true fallback | high | mitigate | Task 2 explicitly forbids `results[qId] = true` and `results[qId] = "FAILED"` — every failure path sets `verdict: "ungraded"` locally. The negative-grep check in the automated verify enforces this at plan-commit time. Removes the existing regression at Code.gs L177. |
| T-10-01d | Denial of Service | Gemini API timeout / prolonged latency | medium | accept | The 6-minute Apps Script execution cap remains as the outer bound (RESEARCH.md Pitfall 3); this plan does not raise the batch cap of 5 attempts per drain. Wave 3 (plan 10-07) instruments live wall-clock timing to detect if the ungraded rate exceeds ~5% in production. |
| T-10-01e | Tampering | Rubric weight per question sums to != 1.0 | low | mitigate | Task 1 requires weights sum to 1.0 ±0.01; plan 10-04 sync-check adds a `has()` assertion that the rubric-weight-sum property test exists in the mirror. Invalid rubrics would cause skewed criterion-level scoring, not incorrect verdicts. |
| T-10-01-SC | Tampering | npm/pip/cargo installs | n/a | n/a | Plan installs zero packages — Package Legitimacy Gate not applicable. |
