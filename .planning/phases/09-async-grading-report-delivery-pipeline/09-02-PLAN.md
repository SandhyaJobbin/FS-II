<objective>
Create `backend/AsyncGrading.gs`, a new Apps Script file (global scope, shares the same project as `Code.gs` -- no imports) that holds the entire deferred half of the pipeline: the grading logic moved verbatim out of `handleSubmitAnswers`, the candidate/recruiter email builders, and a stateless recurring-trigger worker that drains the `PendingGrading` queue created by plan 09-01.

Purpose: This is the worker-path half of Phase 9 (ROADMAP Phase 9 Success Criteria #2-5). Per 09-CONTEXT.md D-01 through D-12, grading must stay identical to today's scoring logic (moved, not rewritten), candidate and recruiter emails must have deliberately different content (recruiter gets integrity data, candidate never does), and failures must retry a bounded number of times without ever alerting anyone.
Output: `backend/AsyncGrading.gs` with the full grading-extraction, email-building, and queue-drain-worker logic, plus the one-time trigger installer.

Design note on Roadmap Success Criterion #4's `email_status` enum (`pending`/`sent`/`failed`/`retried`): 09-CONTEXT.md's Claude's Discretion section explicitly leaves the exact `email_status` enum value names to research/planning, while the roadmap only locks that the underlying *states* be represented. This plan implements `PendingGrading.CandidateEmailStatus`/`RecruiterEmailStatus` as a 3-value enum (`pending`/`sent`/`failed`, see `sendCandidateEmailIfNeeded`/`sendRecruiterEmailIfNeeded` in Task 2) rather than adding a 4th `"retried"` literal, because retry state is already fully represented elsewhere: `PendingGrading.AttemptsCount` increments on every failed attempt (`recordQueueItemFailure`), and `PendingGrading.Stage` stays `"queued"`/`"graded"` while a row remains retry-eligible and flips to `"permanently_failed"` once D-11's 3-attempt cap is hit. Writing a literal `"retried"` string into the email_status column in addition to that would be a write-only value nothing in this codebase ever reads or branches on. This 3-state design is the intentional realization of Roadmap SC#4's discretion-covered enum, not a missed requirement -- do not add a 4th email_status literal during execution.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Time-based trigger -> `processGradingQueue` | No external caller/input -- rows originate from `PendingGrading`, itself populated only by an already-validated `doPost(submitAnswers)` enqueue (plan 09-01) |
| `AsyncGrading.gs` -> `MailApp.sendEmail` (outbound) | Recipient list for the recruiter path is assembled from a Script Property; misconfiguration risks sending a full report (with violation data) to the wrong address |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-09-01 | Information Disclosure | `sendRecruiterEmailIfNeeded` / `RECRUITER_EMAILS` | medium | mitigate | `RECRUITER_EMAILS` lives in `PropertiesService.getScriptProperties()` (server-only, never returned in any HTTP response); an empty/unset value fails safe to `RecruiterEmailStatus = "failed"` (D-06) rather than guessing a default recipient |
| T-09-02b | Denial of Service | `sendCandidateEmailIfNeeded` / `sendRecruiterEmailIfNeeded` | high | mitigate | Both check `MailApp.getRemainingDailyQuota() < 1` and return `"deferred"` without recording a failed attempt, so daily quota exhaustion never consumes retry budget or trips the 3-attempt permanent-failure cap |
| T-09-04 | Information Disclosure | `buildReportHtml` / `buildCandidateEmail` | high | mitigate | `includeViolations` is the single boolean control point for the violations section; `buildCandidateEmail` always calls `buildReportHtml` with `includeViolations: false`, so there is no separate candidate template that could drift and leak integrity data |
| T-09-05 | Elevation of Privilege / Information Disclosure | `installGradingTrigger` | high | mitigate | Not wired to any `doPost`/`doGet` action or `checkAdminAuth` gate -- only reachable by a manual one-time run from the Apps Script editor (plan 09-06), so no HTTP request can install, reinstall, or tamper with the trigger |
| T-09-07 | Denial of Service | `processGradingQueue` batch loop | medium | mitigate | Each row is wrapped in its own `try/catch` calling `recordQueueItemFailure`; one malformed `SubmittedAnswersJSON` or scoring exception cannot stall or crash the other rows in the same 5-row batch |
| T-09-08 | Repudiation | `recordQueueItemFailure` | medium | mitigate | Every failed attempt writes `LastError` and `LastAttemptAt` before the retry cap is evaluated, so all 3 attempts are inspectable in the sheet even before a row reaches `permanently_failed` |

No package-manager installs in this plan (0 new dependencies) -- Package Legitimacy Gate not applicable.
