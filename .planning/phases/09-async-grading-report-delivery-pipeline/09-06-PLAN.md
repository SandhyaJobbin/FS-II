<task type="checkpoint:human-action" gate="blocking">
  <name>Task 1: Deploy backend changes and configure the async pipeline</name>
  <context>
    This project has no `clasp`/CLI deployment path configured (verified: no `.clasp.json` in the repo, no `clasp` script or devDependency in `package.json`) -- pushing code, setting Script Properties, and running a function once for OAuth consent can only be done through the Apps Script web editor UI, which Claude has no programmatic access to. This is a genuine no-CLI/no-API gap, not a case of Claude choosing not to automate an available path.
  </context>
  <action>
    Human operator deploys `backend/Code.gs` and the new `backend/AsyncGrading.gs` to the live Apps Script project via the web editor, sets the `RECRUITER_EMAILS` Script Property, and runs `installGradingTrigger`/`processGradingQueue` once each from the editor to install the recurring trigger and force initial OAuth consent -- see `<manual-steps>` below for the exact sequence.
  </action>
  <manual-steps>
    1. Open the Apps Script project's web editor for this deployment. Copy the updated `backend/Code.gs` content over the existing `Code.gs` file in the editor, and create a new file named `AsyncGrading.gs` in the editor with the content of this repo's `backend/AsyncGrading.gs`. Save both.
    2. In the editor, go to Project Settings -> Script Properties, and add a property named `RECRUITER_EMAILS` with a comma-separated list of the recruiter team's real email addresses as the value (this sits alongside the existing `GEMINI_API_KEY`/`FALLBACK_API_KEY` properties per 09-CONTEXT.md's canonical_refs).
    3. From the function dropdown at the top of the editor, select `installGradingTrigger` and click Run once. This both creates the 5-minute recurring trigger (D-09, idempotent -- safe even if run twice) and, if this is the first time any trigger-installing code has run, will prompt an OAuth consent screen -- approve it.
    4. From the function dropdown, select `processGradingQueue` and click Run once manually, approving any additional OAuth scope prompts (specifically `MailApp` send permission). This step exists specifically to avoid the first *live* trigger-driven run silently failing on an unconsented scope (a known Apps Script pitfall for newly added trigger functions).
    5. If this project's web app deployment does not automatically pick up saved script changes, create a new deployment version (Deploy -> Manage deployments -> Edit -> New version) so `doPost`/`doGet` serve the updated `Code.gs`.
  </manual-steps>
  <resume-signal>Type "deployed" once RECRUITER_EMAILS is set, installGradingTrigger and processGradingQueue have each been run once successfully in the editor, and the web app is serving the updated code -- or describe what went wrong (e.g. an OAuth scope was denied, a save failed)</resume-signal>
</task>

  </action>
  <what-built>
    The full async pipeline: a fast-enqueue `doPost(submitAnswers)`, a durable `PendingGrading` queue, a 5-minute recurring trigger that grades and emails, a candidate-facing `ThankYouScreen` confirmation, and a backward-compatible admin report-readiness check.
  </what-built>
  <how-to-verify>
    1. Open the live candidate URL and submit a full test attempt end-to-end (start, answer all questions, submit).
    2. Confirm `ThankYouScreen` renders immediately on submit with confirmation copy and "within a few minutes" turnaround language -- no score, no report, no violation data visible anywhere on screen (ASYNC-01).
    3. Close the candidate browser tab entirely (do not leave it open) -- this is the point of ASYNC-02: grading must not depend on an open connection.
    4. Wait up to 5 minutes for the trigger to fire (D-09 cadence), then check the candidate's email inbox: confirm it received a report email containing the overall score, all 3 trait scores, the narrative insight, and the recommendation tier -- and confirm it does NOT contain any violation count or integrity/security section anywhere in the email body (ASYNC-03, D-01/D-04).
    5. Check every address configured in `RECRUITER_EMAILS`: confirm each received an email containing the violation/integrity summary with the recommendation tier visibly highlighted (ASYNC-04, D-02), and that it arrived as one email with all recruiter addresses on it (not one email per recruiter).
    6. Open the admin panel and locate this test attempt: confirm it now displays as report-ready and its report is fetchable/viewable (confirms plan 09-04's `READY_STATUSES` fix and ASYNC-02's "still observable" guarantee).
    7. Open the `PendingGrading` sheet directly in Google Sheets: confirm this attempt's row shows `Stage = "done"`, `CandidateEmailStatus = "sent"`, and `RecruiterEmailStatus = "sent"` (ASYNC-05 -- delivery status is tracked, not silently dropped).
    8. Optional stress check: submit a second attempt, then immediately submit the exact same `attemptId` again (e.g. by resubmitting from dev tools or a duplicate tab) -- confirm no second `PendingGrading` row is created and no duplicate emails are sent (idempotency guard from plan 09-01, T-09-02a/T-09-03).
  </how-to-verify>
