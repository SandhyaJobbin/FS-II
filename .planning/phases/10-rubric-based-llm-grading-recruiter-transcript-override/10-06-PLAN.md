<objective>
Replace the generic section-default rubric skeletons that plan 10-01 Task 1 seeded with production-quality per-question rubric criteria for all 50 rubric-graded questions (40 open_text + 10 hybrid). This is the ONLY content-authoring plan in Phase 10 — everything else is structural code, and structural code with generic rubrics grades every "sentence correction" question against the same three abstract criteria rather than what THAT specific question tests. This plan closes that gap.

Purpose: Structural code (plans 10-01/02/03) landed the shape of the rubric pipeline; sync-check code (plan 10-04) landed the drift guards; UI code (plan 10-05) landed the surface area. Without this plan, the live pipeline in plan 10-07 would grade every sentence-correction question against "Grammar & Mechanics / Meaning Preservation / Professional Tone" regardless of what specific error the question is designed to test (e.g. a subject-verb agreement question would be scored on tone rather than agreement). A rubric that isn't tailored to the question silently reduces grading signal. Because rubric-quality cannot be automated-verified (there is no test for "is this rubric actually good"), this plan is HUMAN-VERIFY-gated. Claude proposes tailored criteria per question; a human reviewer approves each before commit. RESEARCH.md A4 explicitly documents this as either an in-phase content pass or backlog 999.4 — this plan brings it in-phase because Phase 10's core promise (transparent, principled rubric grading) is undermined by shipping with generic rubrics.

Output: `backend/Code.gs` with 50 production-quality rubric blocks. A recorded human sign-off that all rubrics were reviewed.
</objective>

The shape stays identical to plan 10-01 (`rubric: { version: 1, criteria: [{name, weight, description}, ...] }`) and weights still sum to 1.0 ±0.01. What changes: each `description` field is rewritten to name the SPECIFIC error the question tests. For example, a stem like "Customer didn't sent the screenshot so we can't verify nothing" tests (a) subject-verb / past-tense agreement in "didn't sent → didn't send", (b) double-negative resolution in "can't verify nothing → can't verify anything" or "can verify nothing", (c) minor tonal polish; so the "Grammar & Mechanics" criterion's description becomes `"Subject-verb agreement corrected (didn't sent → didn't send); double-negative resolved (can't verify nothing → can verify nothing or can't verify anything)"` — SPECIFIC to this question — rather than the generic default `"Subject-verb agreement corrected; double-negative resolved."`. Criteria NAMES (`Grammar & Mechanics`, `Meaning Preservation`, `Professional Tone`) may stay the same across the section OR be renamed per-question if the question tests something not covered (e.g. `"Punctuation & Capitalization"` for a comma-splice question). Weights may be re-tuned per question (e.g. a question that primarily tests tone gets Professional Tone weight 0.6 rather than the section default 0.2), but weights ALWAYS sum to 1.0 ±0.01. Do NOT change `stem`, `model_answer`, `id`, `bank`, `section`, `response_type`, `difficulty_tier`, or any other field. Do NOT change the shape of the rubric block — only the content of its inner fields. If a question's `stem` is short enough that only one meaningful criterion applies (rare — check if the question is well-formed), keep a minimum of 2 criteria for reproducibility (single-criterion rubrics collapse to boolean grading and undermine the transparency benefit).
